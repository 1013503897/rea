# Browser/Electron code-mode pilot: 2026-10-15

Decision: **inconclusive about the benefit of actual code composition; improve
the experimental interface before scaling**. This Terra-high pilot did not
demonstrate reliable composition. Preserve the unsuccessful outcomes.

Ten scored attempts used actual shipped Obsidian 1.14.4 and a frozen startup
capture from the real public Excalidraw application. The initial four-question
cohort produced 4/4 successful direct answers and 3/4 successful code answers.
The code identity answer mistyped one node ID. A separately declared dependent
module-read follow-up succeeded with batched direct calls and failed in code
mode. Failed tasks cannot be credited as token savings or faster completion.

## Scope and validity

Production runtime was built from fresh main `6688ed6db`, pinned Node 24.18.0,
npm 11.16.0. Model configuration was `gpt-5.6-terra`, reasoning `high`, through
Codex CLI 0.161.0. The requested alias/configuration is observed; a different
underlying service model identity was not independently verified.

Native direct-MCP versus native code-mode could not be established. Requested
direct settings still invoked `exec`; disabling the code host rejected that
operation. An app-server dynamic-tool preflight also failed to dispatch even
one registered callback with the host disabled. The model said it had called
the tool; **no actual dynamic callback occurred**. Enabled-host session calls
worked in the earlier infrastructure smoke. These are excluded preflights.

Scored runs instead use the common external JSON action protocol described in
README.md. No scored run invoked native tools. Direct actions return complete
production structured results, with existing summaries/selectors/views allowed.
Code actions run agent-written JavaScript through the same SDK backend in an
isolated QuickJS 0.31.0 guest. Both see the same relevant two-tool menu and
original contracts on demand. Original complete SDK replies remain retained.

Each action uses a fresh CLI invocation and replays the history. Thus round
count also changes repeated client instructions, schema exposure and startup
cost. This is a controlled protocol pilot, not native production latency.

Artifact bytes, task files and expected facts were frozen before the scored
samples. The first cohort alternates arm order by question, one repetition.
The adaptive follow-up enables direct batches and explicitly instructs code-side
projection, with code first in one pair. It is a distinct condition, not a
replacement for the first cohort or a statistically controlled replication.

Both backends use the same 512 MiB parent heap policy and production worker
limits. Semantic graphs can be truncated; dynamic available-heap metadata and
parent Evidence identities differ. Selected task facts agree with separate
producer oracles, but byte-identical complete-information parity is unverified.
This study cannot establish a causal advantage of information organization.

## Local resources and discovery

All trials ran serially with one CPU, an 8 GiB whole-scope hard cap, 6 GiB
early stop, no swap, 192 tasks, at least 12 GiB host available memory at start,
and a 4 GiB host reserve. Every scored payload-exit receipt verified cleanup
and zero OOM/limit events. Transient whole-scope final counters disappeared;
**they remain unknown**, rather than being substituted with payload counters.
Kernel cgroup memory includes process-family memory and charged cache, not
summed process RSS. The maximum scored peak was 1,210,003,456 bytes (1.13 GiB).
Initial build/native preflights used the earlier 4 GiB default.

These are fresh backend/model sessions with an already built runtime and warm
host filesystem caches. No intentional cold-cache flush or repeated warm

## What the traces show

- Initial code cells were RPC wrappers printing complete results; none performed
  a meaningful programmatic join, filtering or aggregation. Their lower round
  counts are not evidence for a code-composition mechanism.
- Excalidraw code used 59,768 input tokens versus direct 74,055, but code uncached
  input was 59,768 versus direct 58,183. Code question time was 60.55 s versus
  56.84 s. Fewer total input tokens did not imply less uncached work or faster
  completion in this pair.
- Both modes repeatedly investigated facts already present in the summary and
  encountered ambiguous `main.js` item selectors. Discovery, provenance metadata,
  extra calls and retries matter even when the relevant menu contains two tools.
- Code's identity answer substituted one long ID. Access to JavaScript did not
  prevent the final model response from corrupting an identifier.
- The dependency follow-up asks for external literal specifiers and occurrence
  counts across all 23 main.js module identities, excluding duplicate unresolved
  references. Direct used actual batches, retrieved item facts and correctly
  returned ten external modules, without claiming runtime loading. Code copied
  an invalid ID, did not compose its reads, and returned an unfinished progress
  string. Its smaller token/time totals are **failed-task costs**, not savings.
- Both modes correctly refused to equate one static sender-check observation
  with authorization enforcement for every IPC handler. Neither claimed a
  vulnerability from missing coverage.

## Decision and next experimental change

Do not scale this wrapper protocol or treat these results as a reason to replace
REA's current interface. The useful signal is that a code tool's availability
alone did not produce effective composition, while metadata/discovery and exact
identity preservation are measurable burdens. The hypothesis about competent
code composition remains untested here.

The next bounded study should establish a natural tool-feedback loop that can
actually expose distinct treatments; freeze equivalent retained Evidence; permit
baseline batching; test generic typed/discoverable code primitives on a real
application question; and verify actual agent-written composition before scaling.
Retained materialized answers that avoid identifier retyping are another factor
worth testing separately. Dossier versus primitives versus retained views was
not compared in this pilot. No cache or analysis-speed optimization is claimed.

## Reproduction and evidence

Executed validation: pinned runtime build; 63 existing analysis-efficiency
Python tests; four grader boundary tests; two real SDK/sandbox lifecycle tests;
Python compilation and JavaScript syntax checks; affected-file formatting;
`npm run check:fast` (typecheck and lint). The final fast check completed in
56.23 seconds with a verified kernel peak of 4,545,388,544 bytes (4.23 GiB),
zero observed OOM/limit events and verified payload cleanup. The 8/6 GiB
memory limits, zero swap, one-CPU quota/affinity and task ceiling were also
read from the actual owned kernel cgroup and asserted before that check.

Local evidence root: `/tmp/rea-codemode-experiment-20261015`. It contains pinned
acquisition receipts, full original SDK responses, prompts/actions/observations,
selected Codex tool/usage traces, answers, frozen plans/oracles and resource
receipts. `cohort/review.json` and `dependencies/review.json` are machine-readable.
Raw artifacts, credentials, runtime packages and temporary plans are not committed.
Temporary auth/account profiles were deleted after every trial and preflight.

Executed v1/v2 sources are retained in `sources-v1/` and `sources-v2/`. V1 source
hashes were measured at receipt time; a measurement-only usage-field patch landed
during the first trial, so those digests do not attest to exact loaded driver
bytes. V2 hashes were captured at startup. Subsequent changes only strengthen
argument validation and teardown failure paths; no scored answer was rerun or
repaired. The production runtime stayed pinned throughout.
